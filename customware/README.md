# customware/

This directory captures the fork-local patches that ride on top of upstream.
Each numbered entry has two files:

- `NNN-<slug>.md` — the plan, including any deviations noted under
  "Implementation notes" after the work shipped.
- `NNN-<slug>.patch` — the diff at the time the entry was sealed, used as the
  primary rebase tool on the next upstream update.

`CHANGES-<old>-to-<new>.md` records each upstream update: per-entry outcomes,
conflicts and how they were resolved, and the test baseline the result was
verified against.

## Tags

`v<upstream-version>-customware.<n>`.

`<n>` is a **monotonic event counter**, not the number of entries. It increments
on every customware event — adding an entry, an upstream update, or re-authoring
an existing entry in place. It was originally intended to equal the entry count;
that broke the first time an entry was re-authored without adding a new one
(`v3.2.4-customware.5` re-authored 001 and left the count at four).

## Patch anchors

Patches are anchored on the **upstream release tag** this fork tracks
(`git diff v3.2.4 HEAD -- <paths> ':(exclude)customware'`), not on
`upstream/main`. Upstream's release lines are disjoint — `v3.1.5` is not an
ancestor of `v3.2.4`, and the public `main` branch trails the release tags — so
`upstream/main` is the wrong anchor and produces nonsense diffs.

`':(exclude)customware'` is mandatory. Without it a naive range picks up the
`Restore customware/` commit and embeds the `.md` and `.patch` files inside a
patch, which the composition check will not catch. Exclude the *directory*: at
least one real source file has `customware` in its name.

Composition is verified by applying every patch in order onto a clean worktree
of the upstream tag and diffing the result against `HEAD` excluding
`customware/`. That diff must be empty.

# Binary-format divergence policy

**Fork data lives only in fork-owned keyspace. Upstream-owned wire formats are
never modified.**

This is the most important rule in this directory. It was learned the expensive
way and it is not negotiable without re-reading the reasoning below.

## What went wrong

customware/001 added an `id_generation` field to `TableDefinition`, an
upstream-owned `#[revisioned]` struct, claiming `#[revision(start = 3)]`. That
was correct against v3.1.5.

Upstream then took revision 3 for its own `cache_lives_ts` field in the 3.2
line. Two different layouts now wore the same revision number, so a
`TableDefinition` written by either side decoded at the wrong offset on the
other:

```
A deserialization error occured: Invalid revision `0` for type `IdGeneration`
```

Bumping the fork's field to revision 4 fixed compatibility with upstream data
and silently broke it with the fork's own prior data. That is not a bug that
gets fixed once — upstream will take 4, then 5, then 6. **Every collision is a
breaking data change, and the mitigation ("bump again next rebase") is itself a
breaking data change.**

## Why the obvious escape hatches do not exist

- **Reserve a high revision range for the fork.** `revision-derive` validates
  contiguity at compile time (`resolve_history`: *"revisions must be contiguous
  starting from 1"*), for both the legacy `revision = N` form and the
  new-style entries. A gap is a compile error, and the legacy form synthesises
  one decode arm per revision, so a large `N` is also a codegen blow-up.
- **Dispatch on the revision number at runtime.** There is no such hook. The
  decode arms are generated by the macro from the declared history.

## The rule, and what it costs

Store fork state under a fork-owned key tag instead. The value type is then
fork-owned too, so its revision number belongs solely to this fork and can be
bumped freely.

`key/table/ig.rs` is the worked example: a table-scoped `!ig` key holding
`IdGeneration`. Upstream's table-scoped tags are `!ev !fd !ft !ix !lq`. A key
placed under `key::table::all::TableRoot` is removed automatically by the single
prefix delete in `REMOVE TABLE`, so no cleanup code is needed.

Costs, all of which turned out to be small:

- One extra read per (statement, table), loaded beside the other per-table
  definitions in `NsDbTbCtx::load`.
- Explicit lifecycle on the paths that *set* the policy (DEFINE, ALTER) — the
  paths that delete it are covered by the existing prefix sweep.
- `INFO` and export must join the sidecar back in. Both do so only when the
  value is non-default, which is what keeps output byte-identical to upstream
  for tables that do not use the feature.

The upside is not just avoiding the collision: `TableDefinition` returned to
byte-identical with upstream, the fork's compat snapshot (124 fixtures) was
deleted, and three test files reverted to upstream verbatim. **Following this
rule made the fork smaller.**

## If the rule cannot be followed

The rule covers anything expressible as new keys or compute-layer code, which is
everything on the current roadmap. Should something genuinely require changing a
layout upstream owns, the designed-but-not-built contingency is a
**two-dimensional revision scheme**:

- Set the high non-sign bit of the `u16` revision to mark "this fork" and keep
  the remaining bits as upstream's revision number. The revision is varint
  encoded, so this costs two extra bytes per value.
- Carry a second fork-revision counter that increments within a given upstream
  revision.
- Provide three migration classes: upstream-revision → the fork's first
  revision, a chain between fork revisions within one upstream revision, and
  the fork's last revision on upstream revision N → the fork's first revision on
  upstream revision N+1, authored as part of each upstream update.

Both directions then fail loudly rather than misdecoding: an upstream binary
rejects the fork's revision number as out of range.

**It was not built** because it requires forking `revision` and
`revision-derive` — a proc-macro serialization framework — to add the second
dimension and the migration dispatch. Upstream moved that crate 0.27 → 0.30 in
about four months and pins exact versions, so every SurrealDB rebase would begin
with a rebase of the derive fork, and miscompiles would surface as
macro-expansion bugs inside serialization. The sidecar rule removes the problem
for a fraction of that cost.

It also does not remove the per-rebase migration: each upstream bump still needs
a class-C migration authored. The scheme makes divergence *versioned*, not free.

A further note on the sidecar rule's side effect, which is a feature: a stock
upstream binary can open, read and export a fork database. Fork-specific
semantics are invisible to it (a Sid is just an integer), which keeps both a
downgrade path and canonical tooling available.
